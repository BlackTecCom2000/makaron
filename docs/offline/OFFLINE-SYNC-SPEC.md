**Document Version:** 1.0.0

## 1. Концепция и архитектура Offline-First

### 1.1 Базовый постулат
Система проектируется по принципу **«Local-First / Offline-by-Default»**:
> Любое рабочее действие пользователя (создание заявки торговым агентом, двухэтапная приемка водителем на рампе в подвале, отметка факта доставки с росписью или фото-чеком, учет сдельной выработки фасовщика) **всегда сначала фиксируется локально** в реляционном IndexedDB-хранилище устройства и считается успешно принятым локальной транзакцией, даже при полном отсутствии мобильной связи и интернета.

## 2. Локальное хранилище данных (Client Storage Schema)

### 2.1 Гарантии сохранности квоты (Persistent Storage)
При старте приложения запрашивается постоянный режим хранения в браузере:
```typescript
if (navigator.storage && navigator.storage.persist) {
  const isPersisted = await navigator.storage.persist();
  console.log(`[Storage] Persistent quota granted: ${isPersisted}`);
}
```
Это предотвращает принудительное вытеснение (eviction) базы данных мобильным браузером при нехватке дискового пространства.

### 2.2 Структура очереди синхронизации (`syncQueue`)
Каждое мутирующее действие формирует атомарную запись в таблице `syncQueue`:
| Поле | Тип | Индекс | Описание |
|---|---|:---:|---|
| `uuid` | string (UUIDv4) | PK | Уникальный клиентский идентификатор мутации (ключ идемпотентности) |
| `entityType` | string | Index | Тип целевой сущности (`orders`, `loadings`, `routes`, `piecework_logs`, etc.) |
| `action` | string | Index | Тип операции (`CREATE`, `UPDATE`, `TRANSITION`, `DELETE`) |
| `payload` | object / JSON | - | Полный снимок измененных данных или дифференциальный патч |
| `clientTimestamp`| ISO 8601 | Index | Время фиксации действия на часах устройства |
| `deviceId` | string | Index | Аппаратный идентификатор устройства |
| `syncStatus` | enum | Index | `LOCAL`, `QUEUED`, `SYNCING`, `SYNCED`, `CONFLICT`, `FATAL_ERROR` |
| `retryCount` | integer | - | Количество повторных попыток отправки |
| `nextRetryAt` | ISO 8601 / null | - | Метка времени для экспоненциальной задержки |
| `error` | string / null | - | Сообщение сервера об ошибке валидации или бизнес-конфликте |

## 3. Протокол передачи и жизненный цикл мутации (Push/Pull Lifecycle)

### 3.1 Жизненный цикл локальной транзакции
1. **User Action:** Пользователь в интерфейсе нажимает «Подтвердить доставку» (с росписью клиента на канвасе).
2. **Local Commit:**
   - В локальной таблице `orders` статус обновляется на `DELIVERED`.
   - Проставляются метки `delivery_confirmed_at`, `geo_lat`, `geo_lng`, `signature_data`.
   - В таблице `syncQueue` создается запись со статусом `QUEUED`.
   - В таблице `audit_logs` создается локальная запись аудита.
   - Пользователь видит мгновенный отклик UI (зеленый бейдж «Доставлено (Офлайн)»).
3. **Trigger:** Детектор сети (`navigator.onLine == true` и `isSimulatedOffline == false`) запускает обработку очереди.
4. **Network Push:** Пакет из $N \le 50$ записей отправляется на `POST /api/v1/sync/push`.
5. **Server Ingestion:**
   - Сервер проверяет уникальность каждого `uuid` в таблице `sync_mutations_history`.
   - Если `uuid` уже был обработан — сервер возвращает сохраненный ранее статус `APPLIED` (идемпотентность).
   - Если `uuid` новый — открывается серверная транзакция, применяются валидационные правила FTD v1.0.
   - При успешном сохранении сервер присваивает `server_version = server_version + 1`.
6. **Client Confirmation:**
   - Клиент получает 200 OK со списком примененных UUID.
   - Статус записи в `syncQueue` переводится в `SYNCED`.
   - Локальная сущность получает статус `SYNCED` и актуальную `server_version`.

### 3.2 Экспоненциальная задержка при сетевых сбоях (Backoff Strategy)
При сетевой недоступности (HTTP 502/503/504, тайм-аут, сетевая ошибка):
$$T_{\text{wait}} = \min\left(T_{\max},\; T_{\text{base}} \times 2^{\text{retryCount}} + \text{jitter}\right)$$
- $T_{\text{base}} = 1.5\text{ сек}$
- $T_{\max} = 60\text{ сек}$
- $\text{jitter} = \text{random}(0, 1000\text{ мс})$

## 4. Матрица разрешения конфликтов (Conflict Resolution Matrix)

При одновременном изменении сущности на сервере и в офлайн-клиенте действуют строгие детерминированные правила:

| Сущность | Сценарий коллизии | Стратегия разрешения | Обоснование |
|---|---|---|---|
| **Заказ (Order)** | Клиент офлайн нажал «DELIVERED» (есть роспись/фото), а диспетчер онлайн нажал «CANCELLED». | **Client Proof Wins:** Заказ фиксируется как `DELIVERED`, а статус отмены аннулируется. | Физический факт передачи товара контрагенту имеет абсолютный приоритет над административным решением в офисе. |
| **Заказ (Order)** | Два агента одновременно офлайн создали заказ для одного магазина с превышением кредитного лимита. | **First Registered on Server Wins:** Первый принятый сервером подтверждается, второй переводится в `DRAFT (EXCEEDED_LIMIT)` с уведомлением супервайзеру. | Защита от кассового разрыва и перелимита дебиторской задолженности. |
| **Погрузка (Loading)** | Водитель ввел сканированные данные офлайн, завсклад изменил состав онлайн. | **Mismatch Triggered:** Сервер фиксирует `MISMATCH`. | Безопасность учета: любые несоответствия состава блокируют рейс до очной сверки завскладом и водителем. |
| **Сдельная выработка (Piecework)** | Работник повторно отправил журнал выработки из-за сбоя кэша. | **Idempotency by UUID:** Дубликат отбрасывается без начисления двойной зарплаты. | Сохранение финансовой целостности фонда оплаты труда (ФОТ). |
| **Справочники (Products, Prices)** | Клиент локально сохранил старую цену, на сервере прайс-лист обновлен. | **Server Price Wins for New Orders:** При оформлении в офлайне фиксируется зафиксированная цена заявки; при синхронизации супервайзер видит предупреждение о дельте цен. | Гарантия исполнения обязательств перед контрагентом. |

## 5. Оптимизация медиа-контента (Canvas & Photo Compression)

1. **Фото-подтверждение доставки:**
   - Исходный снимок с камеры (12–48 Мп) **не сохраняется** в IndexedDB в исходном виде.
   - Клиентский HTML5 Canvas сжимает изображение до разрешения $1280 \times 720$ px с качеством JPEG 0.75.
   - На изображение накладывается неотделимый цифровой водяной знак:
     - Дата и время (UTC + Таджикистан TJT UTC+5)
     - Номер заказа
     - ФИО водителя
     - GPS-координаты с точностью ($\pm N$ м)
   - Итоговый размер файла: $\approx 150 - 250\text{ КБ}$.
2. **Цифровая подпись (Canvas Signature):**
   - Векторная полилиния сжимается в оптимизированный PNG DataURI ($\approx 15 - 35\text{ КБ}$) или SVG-траекторию.

## 6. Аварийное восстановление (Disaster Recovery & Data Export)

Если мобильное устройство повреждено или база данных браузера повреждена:
1. **Локальный аварийный экспорт:** В интерфейсе любой роли доступна кнопка «Экспорт несохраненных данных» (формирует зашифрованный JSON-файл `makaron_emergency_backup_<timestamp>.json` со всеми записями `syncQueue` в статусе `QUEUED` или `CONFLICT`).
2. **Импорт инцидента:** Аудитор или Администратор может загрузить данный JSON-файл в бэкенд через `/api/v1/sync/push` для ручного применения транзакций.
